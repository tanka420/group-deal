# GroupDeal SDK candidate v2

`getCatalog({limit,cursor,q,category,status,metric,sort})` reads anonymous `GET /api/v1/catalog`. Search matches all words against public campaign/product/vendor/license text (case-insensitive Unicode NFKC); category is an exact normalized match. Raw search/category inputs are bounded to 120/80 characters; controls and duplicate query fields are rejected. The response echoes trimmed input, includes widget-backed cards and public deployment category facets. Cursors bind the normalized search/category in addition to deployment/status/metric/sort; clear the cursor after changing filters.

Catalogue summary covers all matching public results, including unloaded pages. `totalGrossCommitted` is cumulative USDC base units from the indexer, not revenue or current escrow; `openCampaignCount` uses the same timing/inventory/terms/rights holds as the public widget. It is explicitly not a canonical chain financial proof. Both reads and cards are rechecked in the purchase journey. PRIVATE/UNLISTED/DRAFT/unbound/archived/other-deployment records never enter catalogue rows, facets or totals.

Public seller profiles use `getSeller(sellerId)` and `listSellerCampaigns(sellerId, options)` (anonymous GET `/api/v1/sellers/:id` and `/api/v1/sellers/:id/campaigns`). Profiles require at least one accessible PUBLIC campaign in the current deployment. Private, unlisted, unbound, archived and other-deployment campaigns are excluded from both counts and discovery. Seller cursors bind the seller ID as well as deployment and filters; they cannot be reused for another seller or the global list.

Counts explicitly cover public campaigns: accepting commitments (indexer timing, inventory, terms and rights), finalized, cancelled, and distinct products. These are not financial proofs or revenue/review/follower metrics. `ACCOUNT_CREDENTIAL_LINKED` means the profile payout wallet is an account credential; existing campaigns retain their own pinned payout wallet. Distribution rights and license/support terms remain per product/deal. Card prices come from the widget snapshot, including final clearing prices and held purchase state. No API key is needed for these public reads.

This package uses authenticated user session tokens. API keys and server custody/signing are not implemented. The repository builds and packs this candidate locally; it has not been published to a registry or accepted through G5/G6.

```ts
import { GroupDealSDK } from "@groupdeal/sdk";

const sdk = new GroupDealSDK({ baseUrl: apiOrigin });
const { operation } = await sdk.prepareDelivery(sessionToken, internalOrderId, stableRetryKey);
const { operation: ready } = await sdk.readyOperation(sessionToken, operation.id);
// Present ready.chainId/hubAddress/principal/calldata to the authenticated seller's wallet.
// Persist the returned transaction hash before waiting for receipt. The SDK never holds wallet keys.
await sdk.submitOperation(sessionToken, operation.id, broadcastHash);
// Capture a public sender/nonce witness while the RPC still sees the broadcast.
await sdk.observeOperation(sessionToken, operation.id, broadcastHash);
await sdk.finishDelivery(sessionToken, operation.id, broadcastHash);
// On timeout/reload, recover the same intent/hash. Do not create another delivery/signature.
await sdk.recoverOperation(sessionToken, operation.id, broadcastHash);
```

`prepareDelivery` reserves actual uploaded file/resource license grants. GroupDeal resource keys grant access to GroupDeal resources; external software activation/invite/webhook providers need their own implemented adapter and evidence. `readyOperation` reserves the signature attempt; pending challenges without a transaction hash still require the recovery workflow documented in the application.

For an existing external/manual delivery, `fulfillOrder(token, internalOrderId, secretContent, txHash)` requires a successful `recordDelivery` receipt whose content proof, seller, Hub and onchain order match. The transaction is verified and projected before encrypted delivery metadata is attached. Caller and principal rights are checked by the API. A callback flag or arbitrary key does not establish delivery acceptance.

`verifyWebhookSignature` verifies HMAC over the exact raw body and strict timestamp. It cannot deduplicate a replay within the timestamp window. `receiveWebhook` also checks the signed event ID/event/timestamp and calls a durable inbox with a stable subscription namespace. The inbox must atomically insert the full event using a unique `(subscriptionId,eventId)` key. A duplicate is acknowledged without another insertion; storage failure must return a retryable HTTP status. Retry and DLQ redrive retain the producer event ID.

See [examples/receiver.cjs](examples/receiver.cjs) for a SQLite inbox receiver. It binds to loopback; put HTTPS and an appropriate egress/proxy policy around a deployed receiver. Process its inbox with a worker; commit the business effect plus inbox completion atomically, or use provider idempotency. The example does not claim software activation or delivery merely after receiving a webhook.

Restored subscriptions require a fresh authenticated seller review before receiving new events. Install the receiver with its existing subscription ID and secret. `prepareWebhookRecoveryReview(session, UUID)` persists an owned command without an outbound request; keep the same UUID after a lost acknowledgement. `verifyWebhookRecoveryReview(session, review.id)` explicitly sends a signed `subscription.review` challenge to the saved endpoint. HTTP 200 alone does not approve it. `answerWebhookRecoveryChallenge(rawBody, headers)` checks exact raw-body HMAC, subscription, bounded expiry and challenge schema, then returns `{response}`: HMAC-SHA256 over `groupdeal:webhook-recovery-response:v1:` plus SHA256(rawBody). Reply HTTP 200 application/json with exactly that object, or 401 when null. Never insert this challenge into the order-event inbox or log its nonce/response. The packaged receiver implements this branch.

`getWebhookRecoveryReview(session, review.id)` recovers status without a second send. A VERIFYING or FAILED response is not approval. Only `enabledForNewEvents` confirms the current configuration/context/deployment binding. Reviews expire after 15 minutes; at most 3 explicit attempts per review and 10 preparations per seller per hour. A persisted 30-second lease prevents parallel sends; an interrupted lease needs an explicit retry with a fresh challenge. Changed setup, recovery context or deployment requires a new review. Logout alone leaves an already verified integration configured. Historical jobs and jobs created before approval retain their holds; approval never replays or clears them. This repository candidate has only local owner/receiver proofs; actual restored receiver/owner and live operation remain unverified.

Run `npm ci --ignore-scripts` and `npm test`. The test packs the artifact, installs it in a separate consumer, typechecks imports, checks local API request contracts and verifies tamper/malformed/replay/concurrent/restart behavior. These are local proofs, not live provider or product-journey acceptance.

Public list/detail share a typed DTO including Product/LicenseVersion public fields and deployment scope. Financial amounts are USDC six-decimal base-unit integer strings. `getWidgetData(internalCampaignId)` reads the anonymous JSON card snapshot with lossless six-decimal display amounts, `priceKind`, deployment and visibility. Finalized deals use the final clearing price; held/ended deals omit a future price tier. The price is per unit before buyer rebate. Eligibility and financial actions belong to the deal journey, with chain verification.

`GET /api/v1/campaigns/:internalCampaignId/widget?lang=vi` (or `en`) serves an actual read-only HTML document; `/widget-data` remains JSON. Copy the embed code from the deal share dialog. HTML refreshes visible cards every 45 seconds and has a manual refresh; failed/private/unbound/archived refreshes remove the old card and deal link. Both responses use `Cache-Control: no-store`. Public and unlisted links are readable by anyone who has them; private deals are unavailable. Already exported images or external copies cannot be recalled after a visibility change.

Configure `PUBLIC_APP_URL` as the canonical HTTPS application origin; an unset origin returns null for both links and disables export actions. The same origin must reverse-proxy `/api/v1` to this backend for the canonical widget URL to work. The HTML widget uses nonce CSP with `frame-ancestors *` to permit public embedding, self-only JSON fetches and no wallet/auth scripts. Keep this policy scoped to the widget route; do not loosen the authenticated application's frame policy. This candidate has not been deployed or accepted through a live product journey.

`listCampaigns({limit,cursor,status,metric,sort})` supports 1–100 rows (default 20), newest/oldest ordering by immutable chain startTime then internal ID, and allowlisted status/metric filters. Cursors are scoped to chain/Hub/sort/filter; use the returned nextCursor, and start a new list after changing filters/deployment. Concurrent new items before the cursor appear on refresh rather than being inserted into an existing page sequence. Public API is anonymous; seller mutation uses an authenticated session.

Public errors expose stable allowlisted codes (VALIDATION, NOT_FOUND, RATE_LIMITED, PROJECTION_UNAVAILABLE, SERVICE_UNAVAILABLE) and a generic message. SDK errors expose HTTP status/code and bounded retryAfterSeconds without reflecting remote error text. The public-read budget is 120 requests per minute per Express peer/IP in each server process. It is not a durable/distributed quota; untrusted Forwarded headers do not select a bucket. Configure a trusted edge/proxy policy before deployed multi-instance operation.

For a pending BUY, `expireBuyOperation(sessionToken, operationId)` asks the API to verify its signed authorization deadline and unchanged identity nonce at canonical chain blocks. It needs no wallet signature and returns `BuyOperation`; an `EXPIRED` operation carries `authorizationExpiry`. A local timer, missing RPC transaction or HTTP 200 with a pending phase does not establish expiry. Existing receipts or changed nonces require recovery. Keep the original history/hash, and request a fresh quote with a new retry key only after expiry is verified. This proof does not create an order, refund, claim or wallet transaction.

`retryDelivery(sessionToken, previousOperationId, stableRetryKey)` rechecks a canonical REVERTED or SUPERSEDED wallet outcome and simulates recordDelivery at a current fixed block. The new operation keeps the original calldata, content proof, encrypted entitlement, grant IDs and reserved licenses. Nothing is returned to general inventory or made downloadable during preparation. Its deliveryRetry links the previous operation and verified outcome/capability. Before a new explicit wallet signature, readyOperation also rechecks the current chain order, principal, terms, delivery SLA and staged resource binding and returns deliveryQuote. Retry preparation never signs automatically. Preserve the retry key across a lost response; different concurrent keys cannot reserve another delivery for that order. Actual buyer access still requires the new successful receipt and PROJECTED operation.
### Account seller-follow API (candidate)

Use getSellerFollow(token, sellerId), updateSellerFollow(token, sellerId, {idempotencyKey, expectedRevision, following, notifyNewDeals, notifyDealUpdates}), getSellerFollowCommand(token, sellerId, UUID), and listSellerFollows(token, {limit, cursor}). These are account preferences with in-app public-event notices. Following does not opt into email or grant purchase, download, wallet or financial authority. Keep the UUID and full input until the exact owned command is acknowledged. A lost acknowledgement is recovered by GET; retry uses the same UUID/input. A 409 requires reading current revision before a new explicit change. The response carries the applied command result and current preferences separately. Hidden sellers remain available for owned unsubscribe without public discovery metadata. Unpublished candidate; deployed API/live acceptance is still pending.


Private support candidate: createSupportTicket, listSupportTickets, getSupportTicket, getSupportCommand, replySupportTicket, setSupportTicketState, assignSupportTicket, removeSupportAttachment, listSupportOperators and downloadSupportAttachment. These require an account bearer token; operator assignment/state permissions are checked by the server against current roles. ACCOUNT is private to its account/operators; ORDER is shared with its buyer/seller/operators. Support status never changes onchain allocations or claim/refund rights.

Buyer resource candidate: `getResourceGrants(token, orderId)` returns owned per-unit file metadata, `accessStatus`, `canRedeem`, `downloadReady` and millisecond timestamps for activation, redemption, license expiry and activation deadline. A null deadline means none was configured. Expired licenses retain their grant/order history; an unredeemed license may independently miss its activation window. Already redeemed grants keep access through their license period.

`redeemResourceGrant(token, grantId, key)` activates the assigned license idempotently. Keep the key private; after a lost acknowledgement, reload grants before retrying. `downloadResourceGrant(token, verifiedGrant)` requests a fresh link, rejects redirects and mismatched metadata/origin/query, bounds the stream to the expected length and verifies SHA-256 before returning bytes. JSON is capped at 1 MiB; supported file types are PDF/ZIP/TXT/PNG/JPEG, at most 16 MiB. These methods do not reserve inventory, sign transactions or prove delivery from an external license provider. Production resource selection and live receipt/provider acceptance remain pending.

Retain the exact UUID/input until the command receipt is acknowledged; revision mismatch requires reading current state. Do not log or persist private messages/files in browser storage. Reads do not retry POST automatically. Attachments: PDF/PNG/JPEG/TXT, 1 MiB each/3 per action/8 MiB per ticket/16 MiB per uploader; downloadSupportAttachment checks bounded length and SHA-256 against authorized detail metadata. Active-PDF marker/signature checks are not an antivirus guarantee; files are downloads, never inline previews. Access expires180 days after ticket closure; removed files are retained encrypted under this policy and backup retention is separate. Packed types and real isolated HTTP integration are local evidence, not deployment/registry/G5/G6 acceptance.
